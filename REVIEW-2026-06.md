### [M] XMODEM receive drops a data block when peer sends an all-padding block (file corruption/truncation)
`src/xmodem.c:144` · correctness

**Issue:** xmodem_save_data() uses a single one-block look-behind buffer. When a newly received block is entirely XM_PAD (0x1a), the code decides NOT to write the previously buffered block: `if (!all_pad) { ... xfer_save_data(xmodem_buffer, xmodem_buffer_len) ... }` (lines 134-140) is skipped. The comment at lines 141-142 claims the previous block "will be written (with trim) at final flush", but immediately afterward line 144 `memcpy(xmodem_buffer, data, length); xmodem_buffer_len = (unsigned int)length;` unconditionally OVERWRITES the buffer with the all-pad block, permanently discarding the previous block. At EOT the flush branch (lines 146-159) only trims/writes whatever is currently buffered — the all-pad block — which trims to zero (lines 149-151) and writes nothing. Net effect: the real data block that preceded an all-padding block is silently lost. This fires in two realistic cases: (1) a transferred binary file legitimately contains a full 128/1024-byte block of 0x1a bytes (mid-file data loss), and (2) a sender that pads to a block boundary by emitting a trailing all-0x1a block (the genuine last data block is dropped, truncating the file). A malicious BBS can trigger this deterministically (send a real block, then a 128-byte all-0x1a block, then EOT) to corrupt every XMODEM file the victim downloads.

**Fix:** Do not overwrite the held-back block. Either keep a second buffer so an all-pad block can be examined without destroying the prior block, or simpler: when the new block is all-pad, treat it as the trailing-padding terminator — flush the currently buffered block with trailing-pad trimming and discard the all-pad block (do not memcpy it in). Equivalently, always write the previous block; only defer trailing-pad trimming to the genuine final (EOT) flush of the last buffered block.


### [M] Windows install scripts put assets where paths.c never looks; fonts and music never copied at all

**Issue:** install-windows.bat sets 'set BINDIR=%PREFIX%\bin' and 'set DATADIR=%PREFIX%\share\cgterm\assets' (lines 6-7) and copies assets there (lines 128-131), but the WINDOWS branch of path_init (src/paths.c lines 141-162) only probes exe_dir\assets (= %PREFIX%\bin\assets), parent\assets (= %PREFIX%\assets), then falls back to exe_dir itself — it never probes share\cgterm\assets. ### [M] Remote PETSCII delete (0x14) triggers out-of-bounds write dirty[-1]
`src/gfx.c:702` · security

**Issue:** A byte from the network in PETSCII mode (the primary C64 BBS mode) flows cgterm.c:427 ffd2(c) -> kernal.c case 20 (gfx_delete, kernal.c:152-154) -> gfx.c gfx_delete(). The else-branch (cursor in column 0) ends with an unconditional `dirty[gfx_cursy - 1] = SDL_TRUE;` (gfx.c:702). When the cursor is at home (gfx_cursx==0, gfx_cursy==0) the inner `if (gfx_cursy)` is skipped and this writes dirty[-1]; when gfx_cursy==1 the inner branch decrements gfx_cursy to 0 first, then also writes dirty[-1]. `dirty` is `static SDL_bool dirty[25];` (gfx.c:38), so dirty[-1] is an out-of-bounds write of sizeof(SDL_bool) bytes before the array. After ffd2(147) on connect the cursor is at (0,0) (kernal.c case 147 -> gfx_setcursxy(0,0)), so a malicious BBS need only send a single 0x14 byte. On the current layout dirty[-1] aliases the preceding `static SDL_bool cursorvis;` (gfx.c:37) so the practical effect is corrupting the cursor-visibility flag, but the negative array index is undefined behavior and layout/optimization dependent.

**Fix:** Guard the dirty marking: in the else branch only set dirty for a valid row, e.g. `if (gfx_cursy > 0) dirty[gfx_cursy - 1] = SDL_TRUE; else dirty[0] = SDL_TRUE;` (or mark dirty[gfx_cursy] which is always in range).


### [M] Unbounded keytable[] write from untrusted .kbd file in testkbd
`src/testkbd.c:153` · security

**Issue:** testkbd reads a keyboard map file (an untrusted-download file type per the threat model) and writes `keytable[value] = key;` where `value` comes straight from `sscanf(linebuf, "%15s %d \n", keyname, &value)` (line 151) with no range check. `keytable` is `char keytable[SDLK_LAST]` (line 12, ~323 bytes). A .kbd line such as `space 9999999` or `space -1` makes `value` an arbitrary or negative index, producing an out-of-bounds write into global memory. Notably the shipped loader in keyboard.c was already hardened for this exact case (apply_mapping() at keyboard.c:207 does `if (value < 0 || value >= SDLK_LAST) return;`), but testkbd.c — which IS a default build target in the Makefile (TARGETS includes testkbd) — was missed by the hardening pass and still writes the raw index.

**Fix:** Bound the index before the store: `if (value < 0 || value >= SDLK_LAST) { printf("value out of range on line %d\n", line); } else if ((key = matchkey(keyname)) != 64) { keytable[value] = key; }`. Mirror the apply_mapping() guard already used in keyboard.c.


### [M] SDL built in fixed /tmp path then 'sudo make install' — local root escalation, no checksum verification
`scripts/install-linux.sh:92` · security

**Issue:** When no known package manager is present, install-linux.sh builds SDL in a predictable world-shared /tmp path and installs it as root with zero integrity verification: 'SDL_BUILD="/tmp/SDL-1.2-build"; mkdir -p "$SDL_BUILD" && cd "$SDL_BUILD"' (lines 92-93), download via 'wget -q .../SDL-1.2.15.tar.gz' or curl (lines 95-97, no checksum/signature check), then 'tar xzf SDL-1.2.15.tar.gz && cd SDL-1.2.15; ./configure; make; sudo make install' (lines 102-105). On a multi-user system, 'mkdir -p' succeeds on an attacker-pre-created /tmp/SDL-1.2-build owned by the attacker, who can then replace the tarball or the extracted source/Makefile between download and 'sudo make install' (classic TOCTOU), getting arbitrary code execution as root. install-macos.sh has the identical pattern at lines 62-78 ('SDL_BUILD_DIR="/tmp/SDL-1.2-build"' ... 'sudo make install').

**Fix:** Build in a private directory created with mktemp -d (mode 0700), verify the tarball against a pinned SHA-256 before extracting, and run configure/make as the unprivileged user with only the final 'make install' under sudo. Apply the same fix to install-macos.sh lines 62-78.


### [M] alloc_next_ts() can spin forever on a crafted BAM (free-count byte lies)
`src/diskimage.c:458` · stability

**Issue:** alloc_next_ts() trusts the per-track free-block *count* byte to decide whether to search a track, then enters an UNBOUNDED inner loop that relies on finding a free sector bit:

```c
  for (ts.track = s1; ts.track <= t1; ++ts.track) {
    if  (bam[ts.track * bpt + boff]) {                 // count byte != 0
      spt = di_sectors_per_track(di->type, ts.track);
      ts.sector = (prevts.sector + interleave(di->type)) % spt;
      for (; ; ts.sector = (ts.sector + 1) % spt) {     // <-- no exit but di_is_ts_free()
        if (di_is_ts_free(di, ts)) {
          di_alloc_ts(di, ts);
          return(ts);
        }
      }
    }
  }
```

di_is_ts_free() (D64 path, lines 344-352) returns 'free' based on the bitmap bit, after confirming the count byte is non-zero. A hostile image can set a track's free-count byte to a non-zero value while marking every sector bit as allocated (bit=0). blocks_free() (line 325) sums the count bytes, so di->blocksfree > 0 and di_write()/di_close() proceed to call alloc_next_ts(). Because no sector is ever reported free, the inner `for(;;)` never terminates -> infinite hang. The same pattern exists at line 473 for the second-side (D71/D81) scan. This is reachable when saving a file into a downloaded/crafted image (xfer.c:909 di_open wb + xfer.c:927 di_write into cfg_dldir; also ui_edit/testimage).

**Fix:** Bound the inner loop to spt iterations (try each sector at most once); if none is free, treat the track as full and continue the outer loop, e.g. `for (i = 0; i < spt; i++, ts.sector = (ts.sector+1)%spt) { if (di_is_ts_free(di,ts)) {...} }`. Do the same at line 473.


### [M] Unbounded out-of-bounds read in macro playback when recording is restarted mid-playback
`src/keyboard.c:620` · stability

**Issue:** kbd_getkey() plays back macros with: `key = macrobuf_key[macro_ctr]; ... if (++macro_ctr == macro_len) { macro_play = 0; }` (src/keyboard.c:615-624). The termination test is equality, not `>=`. macro_len can be reset to 0 while playback is active: the menu key handler starts recording with `macro_len = 0; macro_rec = 1;` (src/ui_term.c:887-889, same pattern in src/ui_chat.c:69-73 and src/ui_edit.c:315-319) without clearing macro_play or macro_ctr. If a user opens the menu and presses C (record) while a macro is still playing (playback delivers one key per kbd_getkey call, so a long macro plays for many seconds), macro_ctr is already > macro_len and `++macro_ctr == macro_len` never becomes true. macro_ctr then increments forever, reading macrobuf_key[4096], [4097], ... past the 4096-byte array (MACROSIZE in src/macro.c) into adjacent .bss and eventually unmapped memory (crash). Worse, each out-of-bounds byte is returned as a typed key and, while connected, transmitted to the remote BBS — disclosing adjacent global-memory contents to the peer.

**Fix:** In keyboard.c use `if (++macro_ctr >= macro_len) { macro_play = 0; }` (and similarly `>=` for the recording stop check at line 582 for defense in depth). Additionally, when starting a recording in ui_term.c/ui_chat.c/ui_edit.c, set `macro_play = 0; macro_ctr = 0;` before resetting macro_len.


### [M] cfg_save_setting leaks input FILE handle when temp file cannot be created
`src/config.c:675` · stability

**Issue:** In cfg_save_setting(): `in = fopen(fname, "r"); out = fopen(tmpname, "w"); if (!out) return;` (src/config.c:673-675). If the temp file cannot be opened for writing (read-only home/config directory, permissions, disk full) but the config file is readable, the function returns without fclose(in), leaking one FILE* / file descriptor per call. cfg_save_setting is invoked on every settings toggle (e.g. ui_term.c SDLK_e: cfg_save_setting("localecho", ...)), so repeated toggles in this environment exhaust descriptors over a session.

**Fix:** Change the error path to: `if (!out) { if (in) fclose(in); return; }`.


### [M] menu_init() leaks menu_surface, cursorsurface and all 6 fonts when called a second time
`src/menu.c:166` · stability

**Issue:** menu_init() unconditionally re-allocates global resources without freeing the previous ones: line 166 `menu_surface = SDL_DisplayFormatAlpha(tempsurface);` overwrites the prior full-screen 32bpp surface; line 187 `menu_font[0] = font_load_font(...)` (and the splash/rotozoom/c64pro/petscii fonts at 203/211/217/224) overwrite the prior Font* allocations; line 228 `cursorsurface = SDL_CreateRGBSurface(...)` overwrites the prior cursor surface. On the FIRST call (from gfx_init, src/gfx.c:300) the globals are NULL so nothing leaks, but menu_init is called AGAIN from gfx_set_columns (src/gfx.c:854) every time the user switches between 40-column PETSCII and 80-column ANSI mode (the 'G' menu key -> enter_ansi_mode/enter_petscii_mode -> gfx_set_columns). Each such switch leaks one full-screen surface (~640x400x4 = ~1MB), the cursor surface, and up to 6 loaded fonts. Note the dedicated font selectors (menu_select_menu_font:1829, menu_select_splash_font:1809) DO free the old font before replacing, proving the maintainers know this is required - menu_init simply omits it.

**Fix:** At the top of menu_init, free any previously-allocated resources before reallocating: if (menu_surface) SDL_FreeSurface(menu_surface); if (cursorsurface) SDL_FreeSurface(cursorsurface); and font_free() each menu_font[] entry (taking care of the aliasing where menu_font[1]==menu_font[0] and fallbacks alias [0]/[2]/[4]). Alternatively add a menu_shutdown() that gfx_set_columns calls before re-init.


### [M] gfx_init/gfx_set_columns ignore menu_init() failure; failure path leaves menu_surface dangling -> later NULL/UAF
`src/menu.c:192` · stability

**Issue:** menu_init() returns 1 on failure but both callers ignore the return value (src/gfx.c:300 `menu_init(gfx_width, gfx_height);` and src/gfx.c:854 same). Worse, two failure paths leave the global menu_surface as a dangling (freed-but-non-NULL) pointer: line 192 `SDL_FreeSurface(menu_surface); ... return(1);` when the menu body font fails to load, and line 234 `SDL_FreeSurface(menu_surface); font_free(menu_font[0]); font_free(menu_font[1]); return(1);` when the cursor surface fails. Because callers don't check the return, execution continues and the very next menu draw (menu_cls/menu_print_menu/gfx_draw_line's menu blit at gfx.c:562) dereferences the freed menu_surface (SDL_FillRect/SDL_BlitSurface deref dst->format). This is reachable whenever a required font BMP (e.g. fonts/homespun_grid.bmp and the 10x12yellow.bmp fallback) is missing or corrupt - exactly the untrusted-download scenario for asset files.

**Fix:** Set menu_surface = NULL after the SDL_FreeSurface calls in the failure paths, and make gfx_init/gfx_set_columns check menu_init's return value and abort/handle the error instead of continuing with a broken menu_surface.


### [M] Rectangle paste writes out of bounds past screen buffer in cgedit
`src/ui_edit.c:281` · stability

**Issue:** In ui_rectanglekey(), the copy operation saves rect_w/rect_h derived from the cursor (max 80x25 for the screen) into the static rect_0400/rect_d800 buffers. The paste case (`case SDLK_v`) then calls `gfx_paste_rect(gfx_cursx, gfx_cursy, rect_w, rect_h, rect_0400, rect_d800)` using the CURRENT cursor position as the top-left, but never clamps rect_w/rect_h against the space remaining below/right of the cursor. gfx_paste_rect (gfx.c:904) does `dirty[rect_y + y] = SDL_TRUE;` (dirty is `SDL_bool dirty[25]`, gfx.c:38) and `gfx_0400[(rect_y + y) * cfg_columns + rect_x + x] = ...`. With e.g. a copied column of height 25 pasted at cursor row 24, `rect_y + y` reaches 48 — OOB write of dirty[25..48] — and the gfx_0400 index exceeds the live screen window (gfx_0400 = gfx_0400_buffer + gfx_maxoffset, only cfg_columns*25 bytes of headroom, gfx.c:240-241), writing past gfx_0400_buffer[80000]. This is reachable entirely via local keyboard: copy a rectangle, move the cursor toward the bottom/right edge, then paste. gfx_copy_rect/gfx_clear_rect are bounded by the screen (cursor is clamped), so only the paste path is unsafe.

**Fix:** Before calling gfx_paste_rect, clamp the paste dimensions to the screen: `int pw = rect_w; if (gfx_cursx + pw > cfg_columns) pw = cfg_columns - gfx_cursx; int ph = rect_h; if (gfx_cursy + ph > 25) ph = 25 - gfx_cursy;` and pass pw/ph. Alternatively add bounds checks inside gfx_paste_rect itself.

### [L] di_load_image() short-read loop overwrites buffer start instead of appending
`src/diskimage.c:660` · correctness

**Issue:** The read loop always reads into the START of the image buffer rather than at the current offset:

```c
  read = 0;
  while (read < filesize) {
    if ((l = fread(di->image, 1, filesize - read, file))) {   // <-- di->image, not di->image + read
      read += l;
    } else { ... }

```

If fread() returns a short count (allowed by the C standard, and observed on pipes/NFS/interrupted reads), the second iteration reads the next file chunk into di->image[0], overwriting the first chunk; the region [l..filesize) is never filled and remains uninitialized (di->image came from malloc(), not calloc(), line 650). ### [L] free_chain()/di_delete() uses unvalidated directory startts before di_free_ts()
`src/diskimage.c:582` · correctness

**Issue:** Every other chain walker (find_file_entry, di_read) first passes the track/sector through next_ts_in_chain()/di_ts_valid(), but free_chain() feeds the FIRST link straight to di_free_ts() with only a track!=0 check:

```c

  for (hops = 0; ts.track && hops < di->size / 256; hops++) {
    di_free_ts(di, ts);                 // <-- ts == rde->startts (raw, attacker-controlled)
    ts = next_ts_in_chain(di, ts);
  }
}
```
